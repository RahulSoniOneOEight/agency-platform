# Milestone B.1B Client Runtime Loading Design

## Goal
Make the shared Flutter prototype load generated client-specific runtime artifacts instead of hard-coded demo directions, fixtures, theme, and resource bindings.

## Design principles
- Keep one shared Flutter prototype app for all clients.
- Python tooling composes one deterministic JSON runtime bundle per client.
- Flutter consumes only the generated runtime bundle and does not understand the repository's client-project directory structure.
- URL contract is `?client=<client-id>&direction=<direction-id>`.
- Unknown clients or directions fail visibly; there is no silent fallback to Direction A.
- Direction cardinality remains 2 or 3, with A+B required and C optional.
- Runtime direction fields use the B.1A canonical runtime contract.
- B.1C resource bindings are included when available and remain canonical semantic IDs.
- CI must run without live external APIs.

## Current gap
The Flutter app still hard-codes A/B/C directions in Dart, reads only the `direction` query parameter, assumes all three directions exist, uses hard-coded demo product/service data, and declares no generated client assets. Meanwhile client-project tooling already produces a manifest, canonical runtime direction JSON, fixtures, theme, and B.1C resource bindings.

## Recommended architecture

```text
client-projects/<client>/
  prototype/prototype-manifest.yaml
  prototype/runtime/direction-*.json
  prototype/fixtures/demo.yaml
  resources/selection.yaml + candidates.yaml
        |
        v
tooling/prototype/build_runtime_bundle.py
        |
        v
apps/prototype_app/assets/generated/<client>.json
        |
        v
Flutter RuntimeLoader
        |
        +-- directions
        +-- fixtures
        +-- theme
        +-- resources
        |
        v
?client=<id>&direction=<id>
```

## Runtime bundle contract
Each generated bundle is a self-contained JSON document:

```json
{
  "version": 1,
  "client_id": "prototype-demo",
  "default_direction": "a",
  "directions": {
    "a": {"id": "a"},
    "b": {"id": "b"}
  },
  "fixtures": {
    "products": [],
    "services": []
  },
  "theme": {
    "seed_color": "#6750A4"
  },
  "resources": {},
  "review": {
    "allowed_directions": ["a", "b"]
  }
}
```

The bundle must be deterministic: same client artifacts produce byte-equivalent semantic content apart from formatting.

## Python tooling
Create `tooling/prototype/build_runtime_bundle.py`.

Responsibilities:
- read `prototype/prototype-manifest.yaml`,
- load every manifest-referenced runtime direction JSON,
- load the fixture pack,
- include theme configuration,
- include normalized B.1C resource bindings when present,
- verify `client_id`, default direction, and allowed directions,
- write `apps/prototype_app/assets/generated/<client-id>.json`.

Create `tooling/prototype/validate_runtime_bundle.py`.

Validation must reject:
- missing/invalid client ID,
- fewer than 2 or more than 3 directions,
- missing A or B,
- bundle key != embedded direction ID,
- default direction not present,
- review direction not present,
- invalid runtime direction fields,
- malformed fixtures,
- invalid theme seed color,
- malformed resource bindings,
- unknown or colliding canonical resource IDs.

`build_prototype.py` remains the source composer and should call the runtime-bundle builder after producing the manifest.

## Flutter runtime model
Create `apps/prototype_app/lib/runtime/`:

- `prototype_runtime.dart`: immutable aggregate for client ID, default direction, directions, fixtures, theme, resources, review configuration.
- `runtime_loader.dart`: loads `assets/generated/<client>.json`, parses JSON, validates requested client/direction, and returns `PrototypeRuntime`.
- `runtime_exception.dart`: typed, user-visible runtime loading failures.
- `resource_binding.dart`: parses canonical B.1C resource bindings.

Update `PrototypeDirection` to the B.1A runtime field names:
- `id`
- `name`
- `strategic_goal`
- `navigation_model`
- `primary_journey`
- `discovery_model`
- `merchandising_model`
- `density`: `compact | normal | spacious`
- `transaction_model`
- `patterns`
- `components`
- `component_variants`
- `required_resources`

The Flutter UI package's current density enum may remain unchanged internally; B.1B owns an explicit mapping from runtime vocabulary to UI vocabulary. No runtime JSON may use the old `airy/balanced/dense` vocabulary.

## Fixture runtime
Replace hard-coded `DemoRepository` data as the source of prototype content. Runtime fixtures are parsed from the generated client bundle.

B.1B only needs to support the fixture fields already generated by current prototype tooling. Missing optional fields use explicit defaults; malformed required fields raise a runtime error.

## App startup
`main.dart` reads both:

```text
client=<client-id>
direction=<direction-id>
```

For local/demo convenience, when `client` is omitted the app may use the checked-in `prototype-demo` bundle as the explicit default client. This is a declared default, not a fallback for invalid client IDs.

If direction is omitted, use that client's `default_direction`.

If an explicit client or direction is invalid, show a governed error screen with the requested value. Do not silently switch clients/directions.

## Direction selector
The selector is generated from `runtime.review.allowed_directions` rather than fixed A/B/C buttons. A two-direction client therefore renders only A and B.

Changing direction updates application state and renders the selected runtime direction. URL mutation is optional in B.1B; preserving valid initial query behavior is required.

## Theme
B.1B consumes only the existing manifest `theme.seed_color` contract. Full token/theme governance remains a later milestone.

## Resource bindings
B.1C output is passed through unchanged as canonical runtime resource bindings. Flutter parses and exposes those bindings, but B.1B does not redesign resource selection or provider policy.

## Generated asset boundary
Add:

```text
apps/prototype_app/assets/generated/
```

and declare it in `pubspec.yaml`.

The reference `prototype-demo.json` is checked in so CI and local Flutter startup have one deterministic regression client. Additional client bundles are generated as needed.

## Error handling
Required visible failures:
- generated client bundle asset not found,
- malformed JSON,
- bundle client ID mismatch,
- unknown explicit direction,
- unsupported direction contract,
- malformed fixture data,
- malformed resource bindings.

The error screen should identify the client/direction and a concise remediation reason suitable for agency developers.

## Tests
Python:
- runtime bundle composition,
- 2-direction and 3-direction clients,
- canonical direction validation,
- fixture/theme/resource inclusion,
- invalid manifest/direction failures,
- deterministic output,
- integration from `compose_prototype()` to generated Flutter bundle.

Flutter:
- parses a valid generated bundle,
- maps B.1A density vocabulary,
- loads 2-direction client without C,
- unknown explicit direction fails,
- unknown client bundle fails,
- fixture data comes from bundle,
- resource bindings parse,
- direction selector reflects allowed directions.

CI:
- repository validation builds and validates the reference bundle,
- Flutter analyze/tests/build web remain green,
- no network access required.

## Out of scope
- Design Contract to Flutter ID normalization beyond what is required to parse B.1A runtime directions.
- Full semantic token/theme engine.
- Production backend or remote runtime service.
- Runtime HTTP loading.
- Screenshot automation and AI visual QA.
- Production CDN/upload.
- Live Pexels or other provider access from Flutter.

## Success criteria
1. `?client=prototype-demo&direction=a` renders from the generated bundle, not hard-coded direction data.
2. A client with only A+B renders only A+B in the selector.
3. An explicit unknown client or direction shows a visible error rather than falling back.
4. Product/service fixture content originates from the bundle.
5. Theme seed and B.1C canonical resources are exposed by runtime.
6. Python validation proves bundle integrity before Flutter consumes it.
7. Repository Validation and Flutter CI pass without external network providers.
